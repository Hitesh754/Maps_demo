# Signals Specification and Verification Policy

**Policy Engine Version:** 1.0.0  
**Status:** Approved  
**Date:** 2026-11-22  
**Platform Codename:** Meridian  

---

## 1. Principles of Independent Verification

Consumer platforms frequently compress disparate verification evidence into a single opaque trust score (e.g. `confidence: 78%`). Meridian enforces an **Independent Signals Architecture**:

1. **Independent Persistence:** Every signal is stored as a distinct row in `event_signals` with its own producer identifier, schema, timestamp, and confidence metric.
2. **No Averaged Scoring:** Signals are never mathematically averaged into a single floating-point number.
3. **Decoupled Verification Capabilities:**
   - Image authenticity confirms that an image was captured by a physical camera sensor rather than generated by AI or edited in Photoshop. **Authenticity never proves capture location or time.**
   - Geographic validation compares device GPS against image EXIF metadata and road geometries. **Geo-validation is an assessment of consistency, not absolute ground truth.**
4. **Deterministic Policy State Machine:** The canonical `verification_state` of a `geo_event` is computed through a versioned, rule-based truth table evaluated whenever signals are created or updated.

## 2. Signal Types & Specification

### 2.1. Signal Type: `ai_detection`
- **Producer:** Asynchronous ML Inference Worker (`internal/inference`, invoking Pothole-Vision model).
- **Payload Schema (`event_signals.data`):**
  ```json
  {
    "model_name": "pothole-vision-yolo",
    "model_version": "1.2.0",
    "is_stub": false,
    "hazard_detected": true,
    "confidence": 0.89,
    "classes": ["pothole"],
    "bounding_boxes": [
      { "label": "pothole", "confidence": 0.89, "box_2d": [0.42, 0.31, 0.68, 0.58] }
    ]
  }
  ```
- **What it Proves:** Indicates visual feature similarity to cataloged road damage within the pixel region of the uploaded media.
- **What it DOES NOT Prove:** Does not prove the image was taken at the reported coordinates; does not prove the hazard currently exists (could be historical imagery); does not prove the severity depth.

---

### 2.2. Signal Type: `authenticity`
- **Producer:** Asynchronous Image Authenticity Worker (`pothole-verify` ELA/Noise analysis).
- **Payload Schema (`event_signals.data`):**
  ```json
  {
    "algorithm": "error_level_analysis_v2",
    "is_stub": false,
    "verdict": "authentic",
    "confidence": 0.94,
    "compression_artifacts_detected": false,
    "clone_stamp_detected": false,
    "ai_generation_markers_detected": false
  }
  ```
- **What it Proves:** Verifies the file conforms to standard camera hardware JPEG/WebP sensor encoding and lacks digital splicing, clone stamping, or diffusion model generation markers.
- **What it DOES NOT Prove:** **Authenticity NEVER proves capture location, capture date, or current road state.** A genuine photo of a pothole taken in 2018 in another country passes authenticity checks 100%.

---

### 2.3. Signal Type: `geo_validation`
- **Producer:** Internal Spatial Validation Worker (`internal/spatial`).
- **Payload Schema (`event_signals.data`):**
  ```json
  {
    "has_exif_gps": true,
    "exif_coords": [73.1812, 22.3072],
    "reported_coords": [73.1813, 22.3071],
    "coordinate_delta_meters": 14.2,
    "exif_timestamp": "2026-11-22T14:28:10Z",
    "submission_timestamp": "2026-11-22T14:30:00Z",
    "time_delta_seconds": 110,
    "nearest_road_distance_meters": 3.1,
    "verdict": "consistent"
  }
  ```
- **What it Proves:** Validates mathematical consistency between client-reported telemetry and embedded sensor metadata, verifying that coordinates intersect the OpenStreetMap road network.
- **What it DOES NOT Prove:** Does not prove the EXIF metadata was not spoofed by a modified camera app on a rooted device. Geo-validation is a claim comparison, not infallible ground truth.

---

### 2.4. Signal Type: `community`
- **Producer:** Citizen corroborations via mobile app (`event_confirmations`).
- **Payload Schema (`event_signals.data`):**
  ```json
  {
    "corroboration_type": "independent_driver",
    "confirming_user_id": "0193567a-bc12-7000-8000-000000000001",
    "user_trust_score": 1.25,
    "distance_meters": 8.4,
    "speed_mps": 11.2,
    "direction_matching": true
  }
  ```
- **What it Proves:** Independent drivers or pedestrians passing through the vicinity confirmed the presence of the road condition.
- **What it DOES NOT Prove:** Does not guarantee immunity to coordinated sybil attacks or community brigade voting.

---

### 2.5. Signal Type: `moderator`
- **Producer:** Municipal dispatcher or verified road authority via Web Dashboard (`internal/reports`).
- **Payload Schema (`event_signals.data`):**
  ```json
  {
    "moderator_id": "0193567a-bc12-7000-8000-000000000002",
    "verdict": "confirmed",
    "action_reason": "Municipal public works work order #8492 issued",
    "adjusted_severity": 4
  }
  ```
- **What it Proves:** Official human-in-the-loop inspection and administrative endorsement.
- **What it DOES NOT Prove:** Does not guarantee instant physical repair.

## 3. Handling Model & Service Downtime

When external ML inference services or internal workers experience outages, timeouts, or network partitions:
1. An `event_signals` row is inserted with `status = 'unavailable'` or `'pending'`:
   ```json
   {
     "signal_type": "ai_detection",
     "source": "model.pothole.v1",
     "status": "unavailable",
     "error": "Connection timed out after 5000ms"
   }
   ```
2. **Rule of Positive Attribution:**
   - **Model downtime is NEVER silently treated as a negative classification (no hazard).**
   - An event with an unavailable AI signal remains in `verification_state = 'unverified'`, relying on community or moderator signals.
   - The event is placed on a retry queue in NATS JetStream with exponential backoff.

## 4. Deterministic Verification Policy Truth Table (v1.0.0)

The canonical state (`verification_state`) of a `geo_event` is determined by evaluating the following ordered rule matrix from top to bottom. The first matching rule applies:

| Rule ID | AI Detection Signal | Authenticity Signal | Geo-Validation Signal | Community Signal Count | Moderator Signal | Derived Verification State | Operational Meaning |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: | :--- |
| **POL-01** | Any | Any | Any | Any | `rejected` | **`rejected`** | Moderator explicitly rejected or revoked report. |
| **POL-02** | Any | `tampered` | Any | Any | None | **`rejected`** | Fraudulent image detected (digital manipulation). |
| **POL-03** | Any | Any | `delta > 500m` | Any | None | **`rejected`** | Severe coordinate contradiction between GPS and EXIF. |
| **POL-04** | Any | Any | Any | Any | `confirmed` | **`moderator_confirmed`** | Official authority endorsement overrides automation. |
| **POL-05** | Any | Any | Any | $\ge 2$ Negative Disputes | None | **`disputed`** | Citizens report road is clear; flag for inspection. |
| **POL-06** | `detected (conf > 0.8)` | `authentic` | `delta < 50m` | $\ge 2$ Independent | None | **`community_confirmed`** | Multi-vector high-confidence verified event. |
| **POL-07** | `unavailable` / None | Any | Any | $\ge 3$ Independent | None | **`community_confirmed`** | Pure community corroboration during ML downtime. |
| **POL-08** | `detected (conf > 0.8)` | `authentic` | `delta < 50m` | 0 or 1 | None | **`unverified`** | Strong initial observation; awaiting corroboration. |
| **POL-09** | `detected (conf < 0.6)` | Any | Any | 0 | None | **`unverified`** | Low-confidence detection; pending community signals. |
| **POL-10** | Any | Any | Any | 0 | None | **`unverified`** | Default baseline for newly ingested observations. |

## 5. Policy Versioning & Audit Requirements

1. Every policy evaluation records the active engine version (`policy_version = '1.0.0'`) in `event_history`.
2. When policy rules are modified, a new policy version (e.g. `1.1.0`) must be deployed as code. Historical state transitions are immutable; existing events are only re-evaluated upon new incoming signals or explicit administrative batch migration.
